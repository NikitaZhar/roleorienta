# Стенограмма проекта

Живой документ (рабочий контракт §0.1, §0.4): что и зачем сделано и простое объяснение каждой
неочевидной конструкции со ссылкой на официальную документацию. Записи `§NN` только
дописываются.

## §1 — Каркас нового репозитория (подэтап 1.1)

**Зачем.** Технический документ §15, подэтап 1.1: основа, на которой строится магистраль доставки
заданий. Бизнес-логики нет.

**Что сделано.**
- `pom.xml` — корневой модуль сборки (packaging `pom`): общие версии и правила для модулей
  `job-api` и `job-worker`. Родитель `spring-boot-starter-parent` 4.1.1 задаёт согласованные
  версии зависимостей Spring и плагинов. https://docs.spring.io/spring-boot/maven-plugin/using.html
- `testcontainers-bom` — список согласованных версий библиотек Testcontainers; импортируется в
  `dependencyManagement`, поэтому в модулях версии не пишутся. Spring Boot 4 этими версиями не
  управляет. https://java.testcontainers.org/
- `maven-checkstyle-plugin` на фазе `validate` с `config/checkstyle/checkstyle.xml` — правила
  контракта (≤5 параметров и полей записей, имена ≥2 символов, JavaDoc у публичных типов)
  проверяются каждой сборкой. https://checkstyle.org/checks.html
- `job-api`: `spring-boot-starter-web` (REST), `actuator` (health), `data-jpa`,
  `spring-boot-starter-flyway` + `flyway-database-postgresql` (миграции схемы; в Spring Boot 4
  автоконфигурация Flyway — отдельный стартер), драйвер PostgreSQL. В `application.yml`:
  `ddl-auto: validate` — Hibernate только сверяет сущности со схемой, создаёт её Flyway;
  `open-in-view: false` — соединение с БД не удерживается на всё время HTTP-запроса;
  `problemdetails.enabled` — ошибки в формате RFC 9457.
- `job-worker`: web (только для Actuator), `actuator`, `data-jpa`, `spring-boot-starter-amqp`
  (RabbitMQ), драйвер PostgreSQL; Flyway не подключён — схемой владеет job-api. Настройки
  RabbitMQ: `publisher-confirm-type: correlated` — брокер подтверждает приём каждого сообщения;
  `publisher-returns: true` + `template.mandatory: true` — сообщение без подходящей очереди
  брокер возвращает, а не теряет. https://docs.spring.io/spring-amqp/reference/amqp/template.html
- Тесты `contextLoads` в обоих модулях на реальных контейнерах. `@ServiceConnection` —
  Spring Boot сам берёт адрес и учётные данные из контейнера Testcontainers и настраивает
  подключение. https://docs.spring.io/spring-boot/reference/testing/testcontainers.html
- `docker-compose.yml` — PostgreSQL 16 (:5433), RabbitMQ 4 с консолью (:5672, :15672), MinIO
  (:9000, :9001); `healthcheck` — Docker сам проверяет готовность сервиса.
- `.github/workflows/ci.yml` — GitHub Actions: JDK 21 и `mvn -B -ntp verify` на каждый push в
  `main` и pull request.
- Документы: README и эта стенограмма.

**Тесты.** `JobApiApplicationTests`, `JobWorkerApplicationTests` — контекст поднимается.

**README** — написан для нового проекта (контракт §0.2).

**Не вошло.** Outbox, leader-lock, задания с повторами, HTTP-клиент, ArchUnit, приёмочные тесты —
следующие срезы подэтапа 1.1.

## §2 — Outbox и публикация в RabbitMQ (подэтап 1.1)

**Зачем.** Магистраль доставки заданий (технический документ §6, §9, §16.2): событие пишется в
БД в одной транзакции с изменением данных и гарантированно доходит до RabbitMQ.

**Что сделано.**
- `V1__outbox.sql` (job-api) — таблица `outbox_event`; частичный индекс по неопубликованным.
- `RabbitTopology` — обменник `roleorienta.jobs`, рабочая очередь, dead-letter обменник и DLQ,
  всё durable. Бины `DirectExchange`/`Queue`/`Binding` Spring AMQP сам объявляет в брокере.
  https://docs.spring.io/spring-amqp/reference/amqp/broker-configuration.html
- `OutboxRepository` — SQL к outbox. `FOR UPDATE SKIP LOCKED` блокирует выбранные строки до конца
  транзакции и пропускает занятые другой репликой — каждое событие отправляет один публикатор.
- `OutboxPublisher` — пачка в одной транзакции: захват → отправка с `mandatory` → ожидание
  подтверждений (`waitForConfirmsOrDie`) → отметка `published_at`. Вернувшиеся как
  немаршрутизируемые (`basic.return`, собираются `ReturnsCallback`) не отмечаются, счётчик попыток
  +1. Нет подтверждений — откат, повтор на следующем тике; возможный повторный приход сообщения
  гасит идемпотентный потребитель по `messageId`.
  https://docs.spring.io/spring-amqp/reference/amqp/template.html#template-confirms
- `OutboxPublisherTick` — `@Scheduled` тик (пауза `app.outbox.poll-interval-ms`), выключается
  `app.outbox.tick-enabled=false`; `@ConditionalOnProperty` не создаёт бин при выключении.
- `OutboxProperties` — запись настроек `app.outbox.*` (`@ConfigurationProperties`,
  `@DefaultValue`); регистрируется `@ConfigurationPropertiesScan` в `JobWorkerApplication`;
  там же `@EnableScheduling` — включает `@Scheduled`.
- Тесты worker создают схему теми же миграциями job-api: Flyway подключён к worker только в
  тестах, `spring.flyway.locations=filesystem:../job-api/...` в профиле `test`.

**Тесты.** `OutboxPublisherTests`: событие доставлено в очередь с id в `messageId` и отмечено;
без привязки очереди событие не отмечено, попытка засчитана, после восстановления привязки
доставлено.

**README** — строка статуса.

**Не вошло.** Потребитель заданий, таблица заданий с повторами, leader-lock — следующий срез.

## §3 — Задания с повтором через БД (подэтап 1.1)

**Зачем.** Технический документ §6, §9, §16.3, §16.12: временный отказ повторяется с растущим
интервалом, прогресс переживает перезапуск, ошибка кода не теряется.

**Что сделано.**
- `V2__task.sql` — таблица `task`: тип, ключ идемпотентности (UNIQUE), параметры, состояние
  QUEUED → RUNNING → DONE / WAITING / FAILED, попытки, срок повтора, аренда. `outbox_event.task_id`.
- `TaskService.enqueue` — задание и событие outbox одной транзакцией; повтор с тем же ключом
  ничего не делает (`ON CONFLICT DO NOTHING`).
- `OutboxPublisher` кладёт id задания в заголовок `taskId`; `TaskListener` (`@RabbitListener`)
  передаёт его `TaskExecutor`.
- `TaskExecutor` — захват `UPDATE … WHERE state = 'QUEUED'` (повторная доставка задание не
  захватит — идемпотентность), обработчик вне транзакции, запись результата. Результат —
  `TaskOutcome` (sealed: `Done`, `Retry`, `Failed`; `switch` проверяется компилятором на полноту).
  Исключение обработчика → FAILED и сообщение в DLQ (`default-requeue-rejected: false`).
- `RetryPolicy` — 5 мин × 2 до 6 ч + до 10% случайной надбавки, не меньше срока источника
  (`Retry-After`); 8 попыток — FAILED. Значения — `app.task.*`.
- `TaskRequeueTick` — раз в 10 с под leader-lock снова ставит в очередь WAITING с наступившим
  сроком и RUNNING с истёкшей арендой (процесс упал).
- `PostgresLeaderLock` — `pg_try_advisory_xact_lock`: не ждёт, освобождается с транзакцией;
  реестр ключей — в JavaDoc класса. https://www.postgresql.org/docs/current/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS
- `TaskHandler` — контракт обработчика; бины собираются через `ObjectProvider` (обработчиков
  может не быть). Обработчики типов появятся с функциями (подэтап 1.2).
- В профиле `test` потребитель не стартует сам (`auto-startup: false`); тесты, которым он нужен,
  запускают его через `RabbitListenerEndpointRegistry`.

**Тесты.** `TaskFlowTests`: постановка → outbox → брокер → потребитель → DONE, повторная
постановка не создаёт задание; повторное выполнение не вызывает обработчик; временный отказ →
WAITING → перепостановка по сроку; последняя попытка → FAILED; истёкшая аренда → QUEUED;
исключение → FAILED и DLQ; неизвестный тип → FAILED. `RetryPolicyTests`: удвоение, потолок,
надбавка, `Retry-After`.

**README** — строка статуса.

**Не вошло.** Выделенный HTTP-клиент, безопасный XML, ArchUnit, каркас приёмочных тестов —
следующие срезы подэтапа 1.1.

## §4 — Чистка: outbox только для заданий (подэтап 1.1)

- `OutboxEvent` — `(id, taskId)`; сообщение без тела: `messageId` — id события, заголовок

  очереди, захвата и выдачи — `JdbcTemplate` с явным SQL (`SKIP LOCKED`, условный `UPDATE …
  RETURNING`, `ON CONFLICT`), в одной транзакции с JPA.

**Тесты.** `OutboxPublisherTests` — событие ссылается на задание; проверяются `messageId` и
заголовок `taskId`.

## §5 — Выделенный HTTP-клиент (подэтап 1.1)

**Зачем.** Технический документ §10: все внешние запросы — через один клиент с защитой от SSRF,
таймаутами и потолками; отказы источника разобраны для повторов (бизнес-описание §4.6).

**Что сделано.**
- Зависимость Apache HttpClient 5 (версия — Spring Boot). Встроенный в JDK клиент сам заново
  определяет адрес хоста и не даёт проверить фактический адрес соединения; в Apache HttpClient
  определение адреса подменяется (`SystemDefaultDnsResolver`). Строка §3 технического документа
  исправлена. https://hc.apache.org/httpcomponents-client-5.4.x/
- `AddressPolicy` — запрещённые адреса: loopback, частные сети, link-local (облачный metadata),
  multicast, 0.0.0.0/8, 100.64/10, fc00::/7, IPv4 в записи IPv6.
- `ExternalHttpClient` — только http/https; каждый адрес, в который разрешилось имя, проверяется
  перед соединением, в том числе на редиректах (защита от DNS-rebinding); таймауты, не больше
  `max-redirects` переходов, циклы запрещены, тело — не больше `max-body-bytes`; встроенные
  повторы библиотеки выключены. `BlockedAddressException` наследует `UnknownHostException` —
  так отказ проходит через клиент как ошибка ввода-вывода.
- `HttpResult` (sealed): `Success`; `TemporaryFailure` — таймаут, обрыв, 5xx, 429 с `Retry-After`
  (секунды или дата); `PermanentFailure` — `ACCESS_DENIED` (401/403), `NOT_FOUND` (404/410),
  `BLOCKED`, `TOO_LARGE`, `CLIENT_ERROR`. Обработчики заданий переводят его в `TaskOutcome`.
- Настройки `app.http.*`; `allow-private-addresses: true` — только для локальных заглушек.

**Тесты.** `ExternalHttpClientTests` на встроенном в JDK HTTP-сервере (без новой тестовой
зависимости): успех с кодировкой, POST JSON, 503, 429 с `Retry-After` секундами и датой,
403/404/400, большой ответ, цикл редиректов, таймаут, блокировка 127.0.0.1, localhost,
169.254.169.254 и схемы ftp. `AddressPolicyTests` — внутренние и публичные адреса.

**README** — стек и строка статуса.

**Не вошло.** Бюджет запросов на хост, robots.txt, безопасный XML — вместе с первым чтением
источника и адаптером Personio (подэтап 1.2).

## §6 — Чтение источника Greenhouse (подэтап 1.2)

**Зачем.** Первый рабочий путь ядра «источник → вакансии» (технический документ §5, §6).

**Что сделано.**
- `V4__source_posting_vacancy.sql` — `source` (провайдер + доска), `vacancy` (состояние, позиция,
  ссылка, даты), `job_posting` (уникальна в паре «источник + внешний id»).
- JPA-сущности `Source`, `Vacancy`, `JobPosting` и репозитории Spring Data
  (`JpaRepository`: готовые операции, запрос по имени метода
  `findBySourceIdAndExternalId`). https://docs.spring.io/spring-data/jpa/reference/
- `SourceAdapter` — контракт адаптера провайдера; `SourceReadResult` — `Read` (публикации) или
  `Unavailable` (отказ `HttpResult`).
- `GreenhouseAdapter` — `GET /v1/boards/{board}/jobs?content=true` через `ExternalHttpClient`,
  разбор JSON (Jackson 2, версия — Spring Boot); не-JSON в ответе — временный отказ.

## §15 — Обходы `CrawlRun` (подэтап 1.2)

**Зачем.** Технический документ §4: обход — одно чтение списка публикаций источника с конечным
состоянием. Раньше итог чтения (полное, неполное, отказ и почему) оставался только в журнале;
теперь он хранится и станет основой показателей источников. Расхождение 2 аудита §11 (частично).

**Что сделано.**
- `V7__crawl_run.sql` (job-api — владелец схемы): `crawl_run` — источник, задание, начало и конец,
  состояние `COMPLETE`/`PARTIAL`/`FAILED`, причина неполноты, вид и текст отказа, число
  публикаций. Две проверки `CHECK` держат согласованность: причина неполноты есть тогда и только
  тогда, когда `PARTIAL`; вид отказа — когда `FAILED`. Внешний ключ на задание с
  `ON DELETE SET NULL`: удаление задания не стирает историю обходов.
  https://www.postgresql.org/docs/16/ddl-constraints.html
- Пакет `crawl`: сущность `CrawlRun` (фабрики `read` и `failed`, `finish` — время записи),
  `CrawlRunState`, `PartialReason` (`PAGE_LIMIT`, `PAGE_FAILED`, `LIST_ENDED_EARLY`),
  `CrawlRunRepository`.
- `SourceReadResult.Read` вместо признака `complete` несёт причину неполноты (`null` — полное);
  фабрики `Read.full` / `Read.partial`, метод `complete()` сохранён. Адаптеры называют причину:
  Workday — отказ страницы, пустая страница раньше `total`, потолок; `JobPosting` — потолок,
  временный отказ страницы.
- `ReadSourceHandler` засекает начало до чтения (бин `Clock`) и передаёт обход в `PostingRecorder`;
  тот сохраняет его **в той же транзакции**, что и изменения публикаций, — итог чтения и его
  запись не расходятся. Конец обхода — момент записи, включая запросы текста.

```mermaid
flowchart LR
  H[ReadSourceHandler: startedAt] --> A[адаптер: Read / Unavailable]
  A --> R[PostingRecorder, одна транзакция]
  R --> P[публикации и вакансии]
  R --> C[crawl_run]
```

Зависимости пакетов без циклов: `adapter` → `crawl`, `vacancy` → `crawl`; `crawl` зависит только
от `source` и `http`.

**Тесты.** `ReadSourceFlowTests` — полное чтение даёт обход `COMPLETE` с числом публикаций и
заданием; 503 — `FAILED` с видом `TEMPORARY`. Тесты адаптеров проверяют причину неполноты
(Workday — `PAGE_FAILED`; `JobPosting` — `PAGE_LIMIT`, `PAGE_FAILED`).

**README** — не менялся (стек, запуск и статус подэтапа не изменились).

**Не вошло.** Обход не создаётся заранее планировщиком (пишется по итогу чтения); контрольная
точка, наблюдения `CrawlObservation`, область с фильтром страны — позже, когда появится обход

## §16 — История вакансий `VacancyRevision` (подэтап 1.2)

**Зачем.** Технический документ §4, §6: история изменений вакансии с первого обнаружения; пишется

**Что сделано.**
- `V8__vacancy_revision.sql`: запись истории — вакансия, публикация-источник, обход, поле

## §30 — Места Workday в оценке страны и формата (подэтап 1.4)

**Зачем.** Живая проверка §29: из 594 вакансий у 230 страна «неясно», почти все — Workday; у них же
ложный формат `OFFICE`. Причины: места Workday записаны как `IND.Pune`; у публикации в нескольких
местах список отдаёт сводку «2 Locations», сами места есть только в детали; шаблонная фраза текста
«in the office or in the field» считалась офисом.

**Что сделано.**
- `LocationResolver`: сегмент места, начинающийся с трёх заглавных букв и точки (`IND.Pune`,
  `USA.VA.Reston`), — страна по коду ISO 3166-1 alpha-3 (трёхбуквенный код страны; соответствие
  двухбуквенному — `Locale.getISO3Country`,
  https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Locale.html#getISO3Country()).
- Формат: гибрид и удалённо — по названию, местам и тексту; офис — только по названию и местам.
  Офис в тексте учитывается лишь рядом с удалённой работой — даёт противоречие (`CONFLICT`,
  оценка «неясно»): иначе случай корпуса «On-site role, work from home occasionally» стал бы
  «удалённо» и исключался бы при поиске офиса. Это уточнение правила из `next-step.md`.
- `SourceAdapter.content` → `detail`: деталь возвращает публикацию (`FetchedPosting`) с местом и
  текстом. `WorkdayAdapter.detail` и `check` собирают места из `jobPostingInfo.location` и

    лимит, `active`. Одна активная версия на пользователя — частичный уникальный индекс

    лимита.
- Время в JDBC-параметрах — `OffsetDateTime` в UTC: тип, который драйвер PostgreSQL сопоставляет
  `TIMESTAMPTZ` (https://jdbc.postgresql.org/documentation/query/#using-java-8-date-and-time-classes).

## §45 — Государственный портал вакансий: работодатели и их вакансии (подэтап 1.7)

**Зачем.** Замер этапа 0 (§44) показал, что у массовых работодателей своей кадровой страницы нет, а их
вакансии — на государственном портале Služby zamestnanosti. Перед кодом портал проверен ещё раз (браузер,
2026-10-02): он показывает не только свои вакансии (12 101), но и объявления profesia.sk (11 853),
worki.sk, kariera.sk и EURES, и сам привязывает каждое к IČO работодателя — запрос `?firma=<IČO>`
возвращает всё вместе. Повторный подсчёт тех же 550 компаний: вакансии на портале у 95 из 500 случайных
(было 51 — считались только свои вакансии портала) и у 39 из 50 крупнейших; портал и своя кадровая
страница вместе — 107 из 113 работодателей, у которых найден хоть один канал; карточек profesia.sk вне
портала — 6. Поэтому отдельный срез profesia.sk не нужен (решение владельца).

**Как работает.**

```mermaid
flowchart LR
  T[StatePortalTick<br/>раз в час под leader-lock] -->|раз в неделю| L[STATE_PORTAL list<br/>список работодателей]
  T -->|раз в день| C[STATE_PORTAL check<br/>по 150 работодателей]
  L --> PE[(portal_employer)]
  PE --> C
  C -->|вакансии есть| S[(source: sluzbyzamestnanosti / IČO<br/>company_source: EMPLOYER)]
  S --> R[READ_SOURCE раз в сутки<br/>?firma=IČO]
```

- **Список работодателей** (`/zamestnavatelia`, около 27 800, по 200 на страницу) раз в неделю
  записывается в `portal_employer` (IČO, название, когда был в списке). Число вакансий в этом списке —
  только свои вакансии портала, объявления площадок оно не считает, поэтому наличие вакансий проверяется
  отдельно.
- **Проверка.** Работодатель, который есть в реестре (по IČO), действует, не кадровое агентство, страна
  сбора активна и у компании нет ни одного источника, проверяется запросом `?firma=<IČO>`: портал
  объявляет число вакансий («8 pracovných ponúk»). Есть вакансии — подключается источник портала (провайдер
  `sluzbyzamestnanosti`, доска — IČO, страна SK) при записанном основании использования, компания
  связывается с ним как работодатель, итог проверки компании — «подключена». Повтор через 7 дней.
- **Чтение источника** — общий механизм `READ_SOURCE`: страницы `?firma=<IČO>&pageSize=50`; карточка —
  название, место, ссылка (своя вакансия портала или объявление площадки); внешний id — uuid портала,
  `profesia:<номер>` или адрес объявления. Полное чтение — только если прочитано столько, сколько объявил
  портал; иначе неполное (`LIST_ENDED_EARLY`), закрытий по нему нет. Текста нет — отбор по названию.
- **Один канал на компанию** (бизнес-описание §4.1): проверка берёт только компании без источников;
  источник портала компании, у которой есть свой источник (кадровая страница), к чтению не ставится
  (`SourceRepository.findToRead`) — его вакансии перестают подтверждаться и уходят по сроку без
  подтверждения, не закрываясь.
- Итог компании пересчитывается так, что компания с любым подключённым источником (в том числе
  порталом) — «подключена» (`CareerScanRepository.COMPANY_RESULT`).

**Конструкции.**
- `portal_employer` (миграция V26) — справочник работодателей портала; `ON CONFLICT … DO UPDATE` обновляет
  известного работодателя тем же запросом, повтор задания дублей не создаёт.
  https://www.postgresql.org/docs/current/sql-insert.html#SQL-ON-CONFLICT
- Задание `STATE_PORTAL` — цепочка заданий ограниченного размера (как обратный путь, §27): шаг и место
  — в параметрах задания (`{"step":"list|check","period":…,"position":…}`), ключ задания содержит
  неделю или день и номер — повторная постановка в тот же период ничего не добавляет. Страниц списка за
  задание — 20, работодателей за проверку — 150 (≈ 1 с на запрос при паузе на хост) — задание
  укладывается в аренду 10 минут.
- Неделя ключа — неделя ISO (`IsoFields.WEEK_OF_WEEK_BASED_YEAR`, например `2026-W40`).
  https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/time/temporal/IsoFields.html
- `SourceRepository.findToRead` — метод Spring Data с `@Query(nativeQuery = true)`: SQL PostgreSQL,
  строки превращаются в `Source`. https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html
- Leader-lock 1010 — постановка работы с порталом (`StatePortalTick`), реестр ключей — в
  `PostgresLeaderLock`.

## §46 — Две очереди заданий: сбор и поиск

**Зачем.** Все задания шли через одну очередь, их выполняли 4 обработчика. Цепочки поиска — приём реестра,
скан Common Crawl, обратный путь, а с §45 и проверка работодателей государственного портала (около
27 тыс. запросов в первые сутки, потом еженедельно) — длятся часами и могли занять все 4 обработчика;
чтение источников, то есть сбор самих вакансий, ждало. На стенде после §45 за ~40 минут проверено 2 700
работодателей портала, подключено 476 источников и прочитано 393 вакансии — нагрузка поиска уже
значительная. Решение владельца: разделить до следующих срезов поиска, чтобы их замеры не искажала
общая очередь.

**Что сделано.**

```mermaid
flowchart LR
  O[(outbox_event + task.type)] --> P[OutboxPublisher]
  P -->|ключ job| W[roleorienta.jobs.work<br/>сбор: READ_SOURCE, MATCH_VACANCIES, RUN_PASS]
  P -->|ключ discovery| D[roleorienta.jobs.discovery<br/>поиск: REGISTRY_INTAKE, SITE_SCAN, CAREER_SCAN,<br/>BOARD_DISCOVERY, STATE_PORTAL, GEO_IMPORT]
  W --> L1[6 обработчиков]
  D --> L2[4 обработчика]
  W -.отказ.-> DLQ[roleorienta.jobs.dlq]
  D -.отказ.-> DLQ
```

- `RabbitTopology` — вторая рабочая очередь `roleorienta.jobs.discovery` (ключ `discovery`) с тем же
  dead-letter обменником и той же DLQ; `routingKey(тип)` выбирает очередь. Типы поиска записаны
  строками: пакет обмена сообщениями не должен зависеть от пакетов обработчиков (иначе цикл пакетов,
  правило ArchUnit) — соответствие константам обработчиков проверяет тест. Прежняя очередь
  `roleorienta.jobs.work` осталась очередью сбора — сообщения, уже лежащие в ней при обновлении, не
  теряются.
- Публикатор outbox берёт тип задания вместе с событием (`JOIN task`); `FOR UPDATE OF e SKIP LOCKED`
  блокирует только строки событий, не задания. https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE
- `TaskListener` — два метода `@RabbitListener`, по одному на очередь; атрибут `concurrency` задаёт число
  обработчиков очереди из настроек (`app.task.collect-consumers: 6`, `app.task.discovery-consumers: 4`)
  вместо общего `spring.rabbitmq.listener.simple.concurrency`.
  https://docs.spring.io/spring-amqp/reference/amqp/receiving-messages/async-annotation-driven.html
- Пул соединений с БД `job-worker` — 15 (`spring.datasource.hikari.maximum-pool-size`): 10 обработчиков,
  тики и публикатор не ждут друг друга. https://github.com/brettwooldridge/HikariCP#gear-configuration-knobs-baby
- Почему не отдельное приложение: тормозит не процессор, а общая очередь и паузы к хосту; отдельные
  экземпляры по очередям — настройкой на этапе 3 (технический документ §2).

**Ключевые файлы.** `messaging/RabbitTopology.java`, `outbox/OutboxEvent.java`, `outbox/OutboxRepository.java`,
`outbox/OutboxPublisher.java`, `task/TaskListener.java`, `application.yml` (job-worker).

**Тесты.** `RabbitTopologyTests` — типы поиска совпадают с константами обработчиков; чтение источников,
соответствия и проходы — в очередь сбора. `OutboxPublisherTests` — задание поиска (государственный портал)
приходит в очередь поиска, а не сбора; прежние проверки публикации — без изменений.

**Документы.** Технический документ §2 (две очереди), §17 (обработчики очередей, соединения с БД);
`docs/next-step.md` — номера следующих срезов сдвинуты на один. README не меняется: модули, стек и запуск

## §55 — Замер поиска кадровых страниц на сайтах стенда

**Зачем.** План (`docs/next-step.md`): перед срезами чтения форматов (SuccessFactors, собственная страница вакансий,

## §56 — Накопленный список, сведения о вакансии, отметки «не подходит» (подэтап 1.5)

**Зачем.** Нарезка 1.5 (§31): после проходов (§31) и учётных записей с условиями (§32) — список, сведения и
отметки через API (технический документ §8; бизнес-описание §4.5, §6; сценарий 13). Решение владельца (§55,
вариант Б): сразу 1.5, форматы крупных компаний — после ядра.

**Что сделано (job-api, пакет `vacancy`).**
- `GET /api/v1/me/vacancies?cursor=&limit=` — накопленный список активной версии условий, новые сверху. Видимость
  — те же правила, что у выдачи job-worker (`DeliveryRepository.PORTION`): не закрыта, подтверждена не раньше
  срока `app.delivery.hide-after` (30 дней, то же значение, что у job-worker), подходит по позиции, стране и
  формату текущих условий, не отмечена. Условия не заданы — пустой список.
- Курсорная пагинация (технический документ §8): курсор — base64url строки «список.время.id» последней строки;
  список — версия условий или «отмеченные»; курсор другого списка или испорченный — `400` (`InvalidCursorException`).
  Сравнение `(время, id) < (?, ?)` — сравнение строк PostgreSQL: страница начинается строго после последней строки.
- `GET /api/v1/me/vacancies/{id}` — сведения (бизнес-описание §6): позиция, работодатель и агентство (компании
  источников публикаций с ролью `EMPLOYER` / `AGENCY`; агентство не подставляется в работодателя), страны,
  формат (противоречивый — «не указано»), территория удалённой работы (страны вакансии с форматом `REMOTE`),
  пометки неопределённости страны и формата, ссылка, даты, состояние, отметка. Полного текста нет. Доступна
  вакансия, которая выдавалась пользователю по любой версии условий или отмечена им; иначе `404`.
- `PUT` / `DELETE /api/v1/me/vacancies/{id}/unsuitable` — отметка и снятие, идемпотентно, `204`. Снятая отметка
  возвращает вакансию в список, если она выдавалась по текущим условиям; иначе её выдаст следующий проход.
- `GET /api/v1/me/unsuitable` — отмеченные, по курсору.
- DTO (`VacancyDtos`) — вложенные записи `Parties`, `Work`, `Publication`: у записи не больше пяти полей
  (checkstyle).
- Тесты: клиент «как SPA» вынесен из `AccountConditionAcceptanceTests` в `ApiTestClient` (общий для приёмочных
  тестов API).

**Ключевые файлы.** `vacancy/VacancyController.java`, `vacancy/VacancyService.java`, `vacancy/VacancyRepository.java`,
`vacancy/VacancyDtos.java`, `vacancy/VacancyProperties.java`, `vacancy/InvalidCursorException.java`,
`web/ApiExceptionHandler.java`, `application.yml` (job-api).

**Тесты.** `VacancyAcceptanceTests` — сценарий 13: две страницы по курсору, закрытая и не подтверждённая 40 дней
вакансии не видны, сведения, отметка и её повтор, отмеченная не в списке и есть в «отмеченных», смена условий —
отметка сохранена, снятие и его повтор; сценарий 14 (список) — чужая вакансия `404`, без условий список пуст,

**Документы.** Технический документ §8 (список). README — API списка, сведений и отметок (§0.2).

## §70 — Цепочки заданий: одна на шаг; задание числа сотрудников укладывается в аренду

**Зачем.** Отчёт по эталону (§69): ядро нашло основной сайт у 248 из 500 компаний. Из 252 без сайта 170 до поиска по
названию не дошли: 147 вне круга — размер неизвестен и источника нет (круг — источник вакансий или 10+ сотрудников,
§53), 23 — в круге, очередь не дошла; ещё 46 — кандидат не подтверждён, 35 — кандидата нет. Размер известен у 4 768
компаний из 504 349 (спрошено 10 486), хотя цепочка по 200 компаний должна давать десятки тысяч в сутки.

**Причина (задания на стенде 2026-10-07).**
- Тик раз в сутки ставит первое задание цепочки с ключом дня. Цепочка вчерашнего дня (`company-size:2026-10-06:46…`)
  ещё шла, а сегодняшняя (`company-size:2026-10-07:1…`) уже началась: две цепочки параллельно берут одних и тех же
  ещё не спрошенных компаний и делят очередь к одному хосту RÚZ (1 с между запросами).
- Задание — 200 компаний, 400 запросов: вчера одно задание шло ~10 мин при аренде 10 мин; с двумя цепочками —
  дольше аренды. Истёкшая аренда возвращает задание в очередь (QUEUED, попытки не растут), оно снова выходит за
  аренду — задания крутятся без конца (на стенде — 7 заданий в QUEUED, обновлялись по 1,5 часа).
- Ключ с днём у цепочек проверки кадровых страниц, адреса по названию и Wikidata — та же беда при цепочке длиннее
  суток (на стенде — две `CAREER_SCAN` одновременно).

**Что сделано.**
- `TaskService.startChain` — первое задание цепочки ставится, только если цепочки этого типа нет:
  `TaskRepository.hasActive` — незавершённое задание типа (QUEUED, RUNNING, WAITING), менявшееся за последние сутки.
  Задание, не менявшееся дольше (потерянное сообщение), цепочку не держит — шаг не останавливается навсегда.
  Используют: `CompanySizeHandler.enqueue`, `SiteNameHandler.enqueue`, `WikidataSiteHandler.enqueue`,
  `CareerScanTick`.
- `CompanySizeHandler` — задание не дольше `app.company-size.task-time-budget` (5 мин; аренда 10 мин): дальше —
  следующее задание цепочки; спрошено меньше взятых — цепочка продолжается.

**Не вошло.** Цепочки скана сайтов (`SITE_SCAN`), обратного пути (`BOARD_DISCOVERY`), портала и предрасчёта — свои
ключи; проверить тем же правилом, если на стенде появятся параллельные цепочки. Задание, вышедшее за аренду,
продолжает работать, пока его копия идёт снова (продление аренды — отдельный вопрос). На стенде `READ_SOURCE` в
QUEUED с 2026-09-29 — потерянное сообщение («Долг»). Круг поиска по названию (147 компаний вне круга) — следующий
срез: после этого среза размер наберётся быстрее, но полный проход всё равно займёт дни.

**Тесты.** `TaskFlowTests.newChainStartsOnlyWhenPreviousOneEnded`. `CompanySizeTests`, `SiteNameTests`,
`WikidataSiteTests` — без изменений (повторный шаг после завершённой цепочки).

## §72 — Решение владельца: три группы компаний и ручной адрес кадровой страницы

**Зачем.** Замеры 2026-10-07 (скрипты `survey/`, вне репозитория): бесплатные источники с разрешённым
автоматическим доступом не дают сайт и кадровую страницу для 90–95 % топ-500. Платные поисковые API владелец
отклонил. Исследование источников — отчёт «Поиск кадровых страниц компаний» (вне репозитория): готового
бесплатного списка кадровых страниц по стране нет; реестры (RPO, RÚZ) сайтов не хранят; путь через материнскую
компанию (GLEIF → Wikidata) даёт сайты групп, а не словацкие кадровые страницы.

**Замеры на топ-500 (поиск сайта v3, кадровые страницы — правила career-search).**
- Сайт и кадровая страница найдены — 245; сайт без кадровой страницы — 97; сайт не найден — 158.
- 97 без кадровой страницы: вакансии на государственном портале по IČO — 46; доска системы найма с упоминанием
  Словакии — 2; только доска без Словакии (jobs.cz — чешские филиалы, чужие компании того же слова) — 9;
  ничего — 40. Доски систем найма по бренду почти бесполезны.
- Причины 97: главная не прочитана — 14; страница строится скриптом — 8; кадровая страница найдена, но отброшена
  нашими правилами — 15 (проверка кадровых слов, ссылка на другой домен, адрес с «é»); на главной нет кадровой
  ссылки — 60 (у 53 нет кадровых слов во всём HTML); чужой сайт по бренду — ~5 (Continental Tobacco →
  continental-tires, Philip Morris → philip.sk, Heineken Distribúcia/Sladovne → потребительский heineken.com).
- 158 без сайта: у 100 адрес по названию угадан, но robots.txt не прочитан (5xx, обрыв) — сайт считается закрытым;
  у 65 есть кандидат (ответ 403, сайт группы).

**Решение владельца (2026-10-07).**
1. Ядро ищет кадровые страницы по текущему алгоритму; компании делятся на три группы: **есть** (кадровая страница
   найдена и читается, или вакансии на государственном портале), **может быть** (сайт найден, кадровой страницы
   нет), **нет** (сайт не найден).
2. Пользователь видит группы. Для интересной ему компании из «может быть» или «нет» он вручную добавляет адрес
   кадровой страницы (или название и адрес).
3. Введённый адрес проверяется: найдена ли кадровая страница, читается ли она. Читается — пользователь видит
   вакансии. Не читается — компания попадает в отдельный список (отдельная вкладка) сомнительных компаний; при
   следующем ручном изменении адрес проверяется снова.
4. Добавленный адрес — общий для всех пользователей.

**Что меняется в плане.** Цель «90–95 % автоматически» снята: автоматический поиск исправляется только там, где он
даёт ложное «есть» или ложное «нет» (чужой сайт по бренду, отброшенные кадровые страницы, robots.txt). Шаг 3 плана
(правда по списку независимым агентом) заменён замерами этого раздела. Ручное добавление — подэтап 1.9
(`CompanyRequest`, технический документ §15) в новом виде.

**Код.** Не меняется. **Документы.** `docs/next-step.md` — план. Технический документ и README — при срезах 1.9.

## §73 — Поиск сайта по названию (шаги 3–4) — как в скрипте замера топ-500

**Зачем.** Решение владельца 2026-10-07: алгоритмы поиска ядра привести к тем, на которых измерен топ-500
(`survey/site-search.py`, `survey/career-search.py`), а результат показать на экране — вакансии и отдельная вкладка
сомнительных компаний. Срезы: §73 — шаги 3–4 поиска сайта; §74 — Wikidata и государственный портал (шаги 1–2);

скриптами провёл отдельный агент (только чтение). Самый большой разрыв — по названию: скрипт нашёл 182 сайта, ядро

**Что сделано.**
- `IcoExtractor` — подписи скрипта: IČO, I.Č.O., IČ, ICO, Company ID, Reg. No., Registration No.; номер из 5–8 цифр,
  короткий дополняется нулями до восьми (как сравнение без ведущих нулей в скрипте). Отличие от скрипта одно:
  подпись внутри слова («Mexico: …») не считается. Правило общее с картой Common Crawl (§25).
- `SiteBrand.confirmed` — бренды скрипта (`keys`: первое слово и два первых слова слитно, без общих слов); правило
  двух слов §51 (`confirmingBrands`) удалено. `SiteBrand.registrable` — регистрируемый домен (`firma.com`,
  `firma.co.kr`).
- `SiteVerifier.check` — итог, конечный адрес и конечный хост после переадресаций; ссылки реквизитов, домен, зона и

  отделён от 401/403 (`CLOSED`).
- `SiteNameHandler` — сайт группы: находка, если регистрируемый домен конечного хоста совпал с доменом сайта

- `StatePortalHandler` — домен почты: запрет robots.txt — сайта нет (`PORTAL_MAIL_403` — только 401/403), как в

**Не перенесено из скрипта.** robots.txt: в скрипте ошибка сервера или сети при чтении robots.txt — запрет
навсегда (из-за этого скрипт потерял 100 компаний топ-500), в ядре — временный отказ с повтором; остаётся как в
ядре. Сравнение бренда в тексте без диакритики (Nestlé → nestle) — остаётся как в ядре.

**Тесты.** `IcoExtractorTests.extractsOtherLabelsAndShortNumbers`; `SiteVerifierTests.firstWordOfNameConfirms`
(вместо `multiWordNameNeedsBothWords`), `brandCheckedOnFinalAddress` (тот же текст после переадресации на чужой хост
сайт не подтверждает), `registrable` в `closedAndGoneSites`; `SiteNameTests.groupSiteConfirmedBySameRegistrableDomain`
(`sk.betaplast.com` из Wikidata подтверждает `www.betaplast.com`).

## §77 — Проверка сайтов на кадровые страницы: несколько сайтов одновременно

**Зачем.** Контрольная выборка после §76 (2026-10-08): сайт проверялся около минуты (после §76 — больше пробных
адресов и хостов: каждый новый хост — чтение robots.txt, несуществующий или зависший — ожидание до 5 с соединения и
20 с ответа). Задание с 50 сайтами шло ~50 минут при аренде 10 минут; прогон эталона — больше двух часов. Скрипт замера
проверял 8 сайтов одновременно. Решение владельца: 6 одновременно, 25 сайтов за задание.

**Что сделано.**
- `CareerScanHandler.checkInParallel` — сайты задания проверяются пулом потоков фиксированного размера
  (`Executors.newFixedThreadPool`, потоки `career-scan-N`; https://docs.oracle.com/en/java/javase/21/docs/api/
  java.base/java/util/concurrent/ExecutorService.html#invokeAll(java.util.Collection)). Пул создаётся на задание и
  закрывается в `try` с ресурсами — `close()` ждёт окончания всех проверок. Ошибка одного сайта, как и раньше,
  завершает задание ошибкой (повтор — таблица заданий); остальные сайты уже записаны.
- Вежливость к сайтам не меняется: промежуток между запросами к одному хосту держит общий бюджет в БД
  (`app.http.politeness.host-interval`, §12) для всех потоков и реплик. Сайты одного задания — разных компаний
  (основной сайт компании), итог каждого — своей транзакцией; общая доска у двух компаний подключается один раз
  (`ON CONFLICT DO NOTHING` ждёт транзакцию, вставившую её первой).
- Настройки: `app.career.sites-per-task: 25` (было 50), `app.career.parallel-sites: 6` — внедряется в конструктор
  `@Value` (в `CareerProperties` уже пять полей — предел контракта, §3.10). `@Value` подставляет одно значение
  настройки, после двоеточия — значение по умолчанию
  (https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/value-annotations.html).
  Соединений с БД: пул 15 (`spring.datasource.hikari.maximum-pool-size`); соединение берётся только на время
  запроса, ожидание ответов сайтов его не держит.

**Тесты.** `CareerScanTests.checksSitesOfTaskInParallel` — три компании с сайтом, ссылающимся на одну доску Workday:
все три проверены одним заданием, доска подключена один раз и связана с каждой компанией.

**Документы.** Технический документ, «Реализовано сейчас» (задания) — `CAREER_SCAN`: 25 сайтов, до 6 одновременно. README не меняется
(§0.2).

**Не вошло.** Почему один сайт проверяется около минуты (пробные хосты, таймауты) — разбор по замеру скорости и
логу job-worker после §77.

## §80 — Кадровая страница на всех сайтах компании, кроме сайтов из Common Crawl

проверяемых сайтов. `nextSites` — не больше одного сайта компании за задание (`row_number() OVER (PARTITION BY
company_id …)` — номер строки внутри сайтов одной компании; https://www.postgresql.org/docs/current/tutorial-window.html):
сайты задания проверяются одновременно (§77), а итог компании пересчитывается по всем её сайтам — два сайта одной
компании в одном задании записали бы итог, не видя друг друга. Второй сайт компании проверяется следующим заданием.

**Тесты.** `CareerScanTests.scansMainAndOtherSitesExceptCommonCrawl` (вместо `scansOnlyMainSite`): основной сайт из

компании, сайт из Common Crawl не проверяется, итог компании — лучший.

## §81 — Кадровые сайты групп, часть 1: поиск кадровой страницы на кандидатах

**Зачем.** План §75, срез 3; решение владельца 2026-10-08 (вариант 1): кадровый сайт группы засчитывается, если на нём

## §82 — Страница компании на profesia.sk: путь к сайту и кадровой странице

**Зачем.** Алгоритм владельца (2026-10-08): 1) сайты компаний → кадровые страницы; 2) портал → объявление profesia.sk →
страница компании на profesia.sk → кадровая страница компании, с которой читаются все вакансии; 3) profesia.sk →
работодатели страны → их кадровые страницы (на случай расхождения портала и profesia.sk). Этот срез — шаг 2. Замер на
эталоне (`target/profesia-*.sh|py`, вне репозитория; 252 компании с вакансиями только с портала): страница компании
на profesia.sk есть у 251; разделы со ссылкой на систему найма («Open positions», как у Henkel → `henkel.csod.com`) —
у 2; прямая ссылка на кадровый сайт или систему найма — у 8 (Lidl, Continental, Mountfield, SCONTO, Mattoni → Nalgoo
…); ссылка на сайт компании — у 87, из них 15 сайтов ядро не находило (Plzeňský Prazdroj, Porsche Inter Auto,
cargo-partner, Tomra, Lyreco, SEAS, Decathlon, TEDi …). robots.txt profesia.sk: страницы компаний открыты,
переадресация отклика `redirect.php` запрещена.

**Решение владельца.** Основание использования profesia.sk (бизнес-описание §10): только путь к сайту и кадровой
странице компании; вакансии с profesia.sk не читаются (они приходят через портал).

**Что сделано.**
- `V42__profesia_company_page.sql` — `portal_employer.profesia_checked_at`; подтверждение сайта `PROFESIA`.
- `ProfesiaSiteHandler` (задание `PROFESIA_SITE`, очередь поиска; ставит `StatePortalTick` раз в день) — по 20
  работодателей за задание (до пяти запросов к profesia.sk с паузой 1 с на хост — в аренде): объявление → страница
  компании → разделы → ссылка; отметка «смотрели» при любом исходе, повтор — через срок перепроверки портала.
- `ProfesiaCompanyPage` — разбор: ссылка на страницу компании (`/praca/<…>/C<номер>`), разделы той же компании
  (`?page_num=`, до трёх), внешние ссылки компании (другой хост, не profesia.sk и не соцсети, вне `#profesia-footer`
  и `header`); выбор — первая кадровая (`CareerLinks.careerLink`: кадровое слово в адресе или доска системы найма),
  иначе первая.
- `StatePortalRepository.employersForProfesia` / `recordProfesia` — работодатели портала в реестре с действующим
  объявлением profesia.sk у источника портала; запись сайта (`STATE_PORTAL`, `PROFESIA`; кадровая ссылка —
  `start_url`); кандидат с тем же хостом становится найденным и перепроверяется.
- `CareerLinks` — публичный класс, `careerLink(url)` для пакета `stateportal`.
- `CareerScanHandler` — стартовый адрес, который сам доска системы найма, — источник; стартовый адрес с кадровым словом
  (`prazdroj.sk/kariera`) и кадровыми словами на странице — кадровая страница.

**Тесты.** `ProfesiaSiteTests`: ссылка на Workday в разделе страницы компании записана сайтом со стартовой страницей
(сайт компании той же страницы проиграл кадровой ссылке); без кадровой ссылки — сайт компании, кандидат с тем же хостом
стал найденным и перепроверяется; разбор страниц (ссылка компании, разделы той же компании, подвал и соцсети не
берутся). `RabbitTopologyTests` — `PROFESIA_SITE` в очереди поиска. Ветка «стартовый адрес — доска» в `CareerScanTests`
не проверяется: заглушка не может быть хостом Workday.

**Документы.** Технический документ §5.1 (шаг 2), README (источники сайтов, §0.2).

**Не вошло.** Шаг 3 (работодатели страны на profesia.sk) — после замера расхождения портала и profesia.sk. Чтение
Cornerstone (`csod.com`, Henkel) — формат не поддерживается.
