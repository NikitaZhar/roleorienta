# Корректировка плана roleorienta

## 0. Как читать документ

Это результат построчной проверки разбора `roleorienta-критический-разбор.md`
против фактического кода репозитория (`git 5ac201d`), миграций и конфигурации.
По каждому серьёзному утверждению стоит вердикт и **точная ссылка на источник**
(файл, строки), чтобы решение принималось по проверенному факту, а не по
формулировке разбора. Раздел 4 — переприоритизированный план под выбранную цель
(гипотеза → стек), с сохранённым ADR-10.

Ничего в коде и в `docs/` этим документом не изменено. Правки техдока/README —
раздел 5, как предложения.

## 1. Вердикт по разбору в целом

Разбор аккуратный и добросовестный. Из 12 пунктов таблицы кода подтверждены все
12; стратегический тезис («инфраструктура доставки построена глубоко, ядро
продуктовой ценности — нет») фактически верен. **Выдуманных дефектов нет** — ни
одного несуществующего файла, метода или инварианта разбор не приписал. Основная
поправка к разбору — не в фактах, а в двух местах, где он обобщает сильнее, чем
есть (раздел 3), плюс одна находка, которой в разборе нет (раздел 2.4).

## 2. Проверенные находки

### 2.1. Подтверждённые дефекты кода (разбор прав)

| # | Находка | Вердикт | Источник (проверено) |
|---|---------|---------|----------------------|
| 1 | Сессия не ротируется при логине (session fixation) | **Подтверждено** | `AuthController.login` — ручная аутентификация, контекст сохраняется в существующую сессию; `changeSessionId()`/`SessionAuthenticationStrategy` не вызывается; в `SecurityConfig` нет `sessionManagement().sessionFixation()`. Не отмечено как известная отсрочка → слепая зона. |
| 2 | `notification` без UNIQUE-ключа | **Подтверждено** | `V21__notification.sql` — есть только `idx_notification_user`; ключа `(app_user_id, job_posting_id, field_name)` (A16/§4/§8) нет. Javadoc `MatchSubscriptionsScheduler` сам признаёт отложенный дедуп. |
| 3 | Outbox-публикатор без потолка попыток | **Подтверждено** | `OutboxEventRepository.claimUnpublished` фильтрует только `published_at IS NULL`; `attempts` инкрементится (`incrementAttempts`), но не читается. Немаршрутизируемое событие перезабирается вечно. |
| 4 | Гонка `ApplicationService.create` → 500 | **Подтверждено** | `ApplicationService.create` — find-then-save без ловли `DataIntegrityViolationException`; `V22` содержит `uq_application_user_posting`. Параллельные POST → 500 вместо идемпотентного ответа (A20). |
| 5 | In-memory ретраи блокируют поток | **Подтверждено** | `job-worker/application.yml` `listener.simple.retry` (stateless, `max-attempts:5`, backoff 1→10s) = `Thread.sleep` на потоке потребителя. Вскроется экспериментом «Недоступность источника» (§13). |
| 6 | N+1 вставок под leader-lock | **Подтверждено** | `MatchSubscriptionsScheduler.match` — на изменение запрос компаний/подписчиков + отдельный `save()` на уведомление, всё в транзакции `PostgresLeaderLock.runIfLeader` (`@Transactional`, весь проход в одной транзакции). |
| 7 | `processed_message` без очистки | **Подтверждено** | `V4__delivery_backbone.sql` — комментарий откладывает retention. |
| 8 | Нет ArchUnit-теста SSRF/XML-пути | **Подтверждено** | В `job-worker/src/test` нет ArchUnit-правил; A13/A14 держатся дисциплиной. |
| 9 | Нет `@ControllerAdvice` с `errors[]` (JSON Pointer) | **Подтверждено** | Во всём `job-api` нет `@ControllerAdvice`/`@ExceptionHandler`; только `spring.mvc.problemdetails` (базовый problem+json). §7/A20 требует `errors[]`. |
| 10 | Нет rate-limit на login/register | **Подтверждено** | `SecurityConfig` — `permitAll` на login/register, троттлинга нет. Брутфорс логина как отсрочка **не** отмечен (в отличие от source-rate-limit, см. 2.2). |
| 11 | IPv6-векторы SSRF неполны | **Подтверждено (низк.)** | `AddressPolicy` раскрывает v4-mapped, покрывает ULA/link-local/site-local/CGN/multicast, но NAT64 (`64:ff9b::/96`), 6to4 (`2002::/16`), Teredo, v4-compatible — нет. |
| 12 | Нет потолка тела ответа | **Подтверждено, уже отслежено** | `SourceHttpClient.getBody` → `.body(String.class)` без лимита; честно отложено в `project-notes §32.6`. |

Плюс две архитектурные заметки разбора подтверждены:
- **Протечка границы ADR-2:** `SubscriptionLookup` читает `company_source` и
  `company_subscription` (таблицы job-api) сырым `JdbcTemplate` — неявная связанность
  по схеме, поймается только контракт-тестом.
- **Весь проход роли — одна транзакция под advisory-локом** (`PostgresLeaderLock`
  `@Transactional`), что подтверждает риск длинной транзакции.

### 2.2. Что уже честно отложено (не слепые зоны)

Потолок тела ответа, source/discovery rate-limit и бюджет обнаружения,
per-host/провайдер лимит гарвеста, XML-адаптер — отмечены как отложенные в
`project-notes §32.6` и `§36.5`. Это гигиена плана, а не пропуск; разбор это
признаёт. **Исключение:** rate-limit на пользовательский вход (login/register/жалобы)
— это другой контур, чем source-rate-limit, и как отсрочка он нигде не зафиксирован.

### 2.3. Стратегический тезис — подтверждён фактически

Проверка миграций (`V1`–`V25`), доменных классов и `CrawlTaskType`:
- **Построено:** магистраль доставки (outbox, брокер, publisher confirms,
  `mandatory`/`basic.return`, DLQ, leader-lock, идемпотентность потребителя),
  планировщик, обнаружение (`DISCOVER_EMPLOYER`, гейт уверенности, гарвест),
  сбор (`DISCOVER_PAGE`/`FETCH_POSTING`), извлечение (навыки/опыт/языки),
  ревизии публикации (`posting_revision`), подписки, уведомления в приложении,
  отклики/заметки/собеседования/жалобы/админ-триаж.
- **Не построено:** `CoverageAssessment`, `Vacancy`/`VacancyRevision`, `MergeLog`,
  `SourceSnapshot`, `CompanyTechProfile`, `AGGREGATE_COMPANY_PROFILE`,
  полнотекст (`tsvector`/GIN), дайджест и email, **второй адаптер (площадка/агрегатор)**
  — реализован только один ATS-адаптер (Greenhouse).

`CrawlTaskType` содержит только `DISCOVER_EMPLOYER`, `DISCOVER_PAGE`,
`FETCH_POSTING` — типы `AGGREGATE_COMPANY_PROFILE`, `REPROCESS_POSTING`,
`MATCH_SUBSCRIPTIONS` в enum отсутствуют (матчер работает отдельным
планировщиком, а не как тип задания).

### 2.4. Находка, которой в разборе нет (двойная проверка)

**Техдок внутренне противоречив после пересмотра ADR-10.** §4 всё ещё описывает
`OutboxEvent` как «используется с Этапа 2… в пилоте не задействовано», а
`PendingChange` — «Работает с пилота (не полагаясь на брокер)», тогда как §2, §3,
§14 и сам ADR-10 вводят брокер и outbox с Этапа 1. Корневой `README.md` тоже
устарел: «Бизнес-логика… ещё не реализованы» при 47 инкрементах. Это чинится
независимо от продуктовых решений (раздел 5).

## 3. Где разбор преувеличивает (осторожно, чтобы не перекорректировать)

1. **«Циклы неограничены (вся пачка pending)».** Неточно: матчер ограничен
   `batch-size:200`, гарвест — `max-fan-out:20`. Реально неограничен только
   `SourceScheduler` (`findByState(ACTIVE)` без пагинации). Значит риск длинной
   транзакции под локом — про планировщик источников при автообнаружении, а не
   про все три роли. Пагинацию имеет смысл вводить прежде всего в планировщик.
2. **Состав «недостроенного ядра» надо разделить.** Кросс-источниковое **нечёткое**
   связывание и техпрофиль компании (`AGGREGATE_COMPANY_PROFILE`) план **сам**
   относит к Этапу 2 (ADR-14, ADR-7, §14) — их отсутствие штатно. Действительно
   недостают из **Этапа 1**: `CoverageAssessment` (даже точное сопоставление +
   состояние «не проверено»), покрытие в ленте/фильтре, второй адаптер-площадка,
   `SourceSnapshot`, дайджест+email. Инверсия последовательности реальна, но
   исправлять надо именно эти пять пунктов, а не тянуть Этап 2 вперёд.
3. **Порядок `basic.return`/confirm в `OutboxPublisher`** — разбор сам называет это
   «тонкостью на проверку», не багом. Согласен: стоит целевого теста с заведомо
   немаршрутизируемым ключом, но подтверждённым дефектом не считается.

## 4. Переприоритизированный план (цель: проверить механизм автообнаружения; охват вендор-инклюзивный; ADR-10 сохранён)

Принцип: цель Этапа 1 — **как можно раньше проверить самую рисковую гипотезу:
приложение само (без ручного ввода списков) находит реальных работодателей и их
карьерные ленты и честно показывает вакансии, которых нет на сравниваемых
площадках.** Охват — по вендор-адаптерам, включая энтерпрайз (Workday,
SuccessFactors, SmartRecruiters; ADR-17). Инфраструктура доставки уже построена и
остаётся (ADR-10) — её не переделываем, только закрываем дефекты, мешающие
безопасному реальному прогону.

### Гейт 0 — прежде чем строить автоматический вход и покрытие

- [ ] **Закрыть Этап 0 документально.** Определить, на каких ATS реально сидят
      компании целевой ниши (для крупных EU-работодателей это часто энтерпрайз —
      Workday, SuccessFactors — а не SMB-ATS); выбрать первый вендор-трек;
      проверить его ленту (поля вкл. зарплату/языки, лимиты, `Retry-After`) и
      **зафиксировать правовое основание повторного использования (A24)** по
      каждому тенанту. Записанный протокол, а не устная проверка.

### Приоритет A — ядро гипотезы (механизм автообнаружения, делаем первым)

Без этого пилот не может проверить собственную гипотезу.

- [ ] **A1. Автоматический вход обнаружения** (Common Crawl / Certificate
      Transparency по вендорному шаблону) — заменяет ручной `seed` как основной
      поток кандидатов. Первый вендор — по Этапу 0, ориентир **Workday** через
      индекс Common Crawl `*.myworkdayjobs.com` (CT для Workday непригоден —
      wildcard-сертификаты, проверено 2026-09-23; протокол Этапа 0 §3).
      *Статус 2026-09-23:* построено (`CcHarvestScheduler`, project-notes §55),
      выключено по умолчанию до B1/B2.
      *Статус 2026-09-24:* включено по умолчанию (B1/B2 выполнены), первый
      контролируемый прогон — project-notes §72.
- [ ] **A2. Проверка принадлежности ленты работодателю в гейте уверенности**
      *Статус 2026-09-23:* минимальная версия — гейт рынка по фасету стран Workday
      (project-notes §56); принадлежность доски конкретному юрлицу — открыта.
      (A11) — сейчас `HIGH` = «лента валидна и непуста», без проверки, чья это
      доска. Это ядро «стабильной работы» механизма.
- [ ] **A3. Дедуп работодателей между входами** (A11) и реальная идентичность
      компании вместо slug-как-имя.
- [ ] **A4. Адаптер(ы) вендоров выбранного входа** (Workday / SuccessFactors /
      SmartRecruiters) за общим контрактом `SourceAdapter`.
- [ ] **A5. `CoverageAssessment`** (сущность + миграция): точное сопоставление
      (§4) + состояние «на площадке»/«только с сайта (скрытая)»/«и там, и там»/
      **«не проверено/неизвестно»** (A01/ADR-15), сравнение против ≥1 подключённой
      площадки; покрытие в ленте/карточке + фильтр «только скрытые». Нечёткое
      связывание — Этап 2 (ADR-14).
- [ ] **A6. `SourceSnapshot` (S3) + привязка `Requirement`→snapshot** —
      объяснимость «навык → формулировка → снимок» (A18/ADR-8).
- [ ] **A7. Дайджест изменений + email** (§7.4) поверх `PendingChange`/уведомлений;
      baseline первой подписки — по A16.

### Приоритет B — высокорисковые дефекты, гейтящие реальный прогон

Делаем **до/вместе с** первым прогоном по реальным источникам (нужен для A1–A3),
т.к. гипотеза проверяется на реальном рынке, а не на заглушке.

- [ ] **B1. Общий бюджет/rate-limit источников + `Retry-After`** (ADR-9, §5/§8) —
      до первого реального сбора, иначе бан источника. *Уточнено 2026-09-23:* два
      разных лимита — вежливость (интервал запросов на провайдера + `Retry-After`) и
      бюджет внимания (сколько деталей в день); объём режется отбором на стороне
      источника (фасеты Workday), а не обрезкой очереди.
      *Статус:* вежливость построена (`RequestPacer`, project-notes §57); бюджет
      деталей — со сбором по рынку.
- [x] **B2. Потолок размера тела ответа** в `SourceHttpClient` (стриминговый) —
      часть SSRF-контура пилота (§9).
      *Статус 2026-09-24:* построено (`app.collect.http.max-body-bytes`, 5 МБ;
      project-notes §71).
- [ ] **B3. Ротация сессии при логине** (`changeSessionId`) — session fixation.
- [ ] **B4. Потолок попыток в outbox** → статус FAILED/карантин, исключение из
      выборки `claimUnpublished`.
- [ ] **B5. Rate-limit на login/register** (и жалобы/предложения) — до любой
      публичной экспозиции.

### Приоритет C — закалка корректности (средний риск, не блокирует гипотезу)

- [ ] C1. `UNIQUE (app_user_id, job_posting_id, field_name)` на `notification` (A16).
- [ ] C2. Ловля гонки `ApplicationService.create` → идемпотентный ответ.
- [ ] C3. `@ControllerAdvice` с `errors[]` (JSON Pointer) для валидации (A20).
- [ ] C4. ArchUnit-тест: внешние вызовы только через `SourceHttpClient`, XML только
      через `SafeXml` (A13/A14 → проверяемо).
- [ ] C5. Retention-джоб `processed_message` по `processed_at`.
- [ ] C6. Пагинация `SourceScheduler` + короткая транзакция на единицу работы;
      N+1 в матчере → set-based `INSERT ... SELECT`.
- [ ] C7. Retry через delayed-exchange/DLQ вместо in-memory backoff.

### Приоритет D — фон / стек (вторичная цель) и низкий риск

- [ ] D1. Раскрытие NAT64/6to4/Teredo/v4-compatible в `AddressPolicy`.
- [ ] D2. CHECK-ограничения на ключевые enum-столбцы (особенно `source.state`).
- [ ] D3. Явный контракт «чтения чужой схемы» воркером (view + контракт-тест) — ADR-2.
- [ ] D4. Реестр ключей advisory-локов (1001/1002/1003/1004) в одном месте.
- [ ] D5. Тест порядка `basic.return`/confirm в `OutboxPublisher`.
- [ ] D6. Продолжение инфраструктуры/стека по §14 (Этапы 3–4) — фоном, не блокирует пилот.

## 6. Открытые вопросы к владельцу

  (энтерпрайз-инклюзивный, ориентир Workday), но конкретная ниша/территория для
