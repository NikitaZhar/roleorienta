# План развития roleorienta

## 0. Принципы (решение владельца 2026-09-25)

1. **Всё автоматически.** Ручное подтверждение не существует: неуверенное ядро пропускает или
   повторяет позже, а не ставит в очередь человеку. Источники компаний — по порядку: (1) открытые
   реестры юрлиц и индексы систем найма (ядро, §1); (2) площадки-агрегаторы как источник названий
   компаний, только с разрешением (E3); (3) ручной ввод компании — только третьим вариантом, как опция по желанию клиента (E4).
   Компания, введённая вручную, проходит тот же автоматический путь (сайт → карьерная страница →
   вакансии), без ручного подтверждения.
2. **Вакансия существует только если она есть на карьерной странице компании.** Название
   компании, её профиль, отрасль, размер — не критерии выбора и не доказательство вакансий.
   Размер компании не используется вовсе (данные о нём часто неверны).
3. **Нет карьерной страницы — компании для системы нет.** Её пропускаем, ссылку не храним.
4. **Читаем только страницы, которые можно разобрать структурно:** система найма с лентой
   (Workday, Personio, Greenhouse …) или своя страница со стандартной разметкой schema.org
   `JobPosting`. Простая страница «Kariéra» без разметки пропускается и не анализируется.
5. **Не нужно найти все компании региона сразу.** Компании берутся порциями; следующий проход —
   следующая порция. Карьерные страницы периодически перепроверяются.
6. **Ниша — на уровне вакансии** (заголовок/описание), а не компании.
7. **Сначала ядро, потом всё остальное.** Интерфейс, сложные фильтры, подписки, отклики,
   аналитика и любой «глянец» развиваются **только после того, как ядро чётко работает**
   (критерий — §3). Уже построенное из этого списка замораживается: не развивается и не чинится,
   кроме поломок сборки.
8. **Признака «скрытая» вакансия/компания нет.** Сравнение с площадками (покрытие) не входит в
   продукт; построенный код покрытия удаляется отдельным срезом (§5).

## 1. Ядро: компании → карьерная страница → вакансии

Порядок пунктов — порядок работы. У пунктов K1–K6 — измеритель; все измерители — в одном отчёте (K7).

- [ ] **K1. Очередь компаний региона.** Источник — открытый реестр юрлиц страны (Словакия — RPO,
      CC BY 4.0): все действующие юрлица региона, **без фильтра по виду деятельности и размеру**.
      Очередь с курсором: за проход — порция N компаний, дальше — следующая; компания, уже прошедшая
      K2–K3, берётся снова только при перепроверке. Реестр отдаёт до 500 записей на запрос и требует
      фильтр — очередь режется по городу и дате регистрации.
      Дополнительный вход того же первого источника — доски систем найма из индекса Common Crawl
      (Workday, Personio; уже построено): доска = компания с карьерной страницей, сразу в K3.
      *Измеритель:* компаний в очереди / пройдено.
- [ ] **K2. Сайт компании — метод поиска.** В реестре сайта нет. Сначала **исследование и выбор
      метода** на выборке (доля найденных сайтов — главный критерий): кандидаты домена по
      названию с подтверждением номера юрлица на странице (IČO; уже построено); открытые каталоги
      (Wikidata); поисковый API (платный, условия проверяются); другие открытые источники, если
      найдутся. Можно сочетать. Принадлежность сайта — только по номеру юрлица на странице.
      *Измеритель:* доля компаний порции с подтверждённым сайтом.
- [ ] **K3. Карьерная страница и её тип.** На сайте — ссылка на раздел вакансий; тип: система
      найма (по адресу/встроенным ссылкам) или своя страница с `JobPosting`; иначе — компания
      пропускается (принцип 4). Хранятся: адрес страницы, тип, дата проверки, состояние.
      **Перепроверка** — периодически (раз в месяц) и сразу, если страница пропала или сменила тип.
      robots.txt сайта соблюдается (до сбора в K4 — обязательно).
      *Измеритель:* доля сайтов с карьерной страницей, распределение по типам.
- [ ] **K4. Сбор вакансий с найденных страниц.** Найденная страница становится источником сбора
      (`Source`) автоматически, без очереди человеку. Адаптеры — по частоте типов из K3: уже есть
      Workday, Personio, Greenhouse; нужен общий адаптер schema.org `JobPosting`; остальные системы
      — по мере того, как K3 покажет их долю. Вакансии, которых больше нет на странице, закрываются.
      *Измеритель:* живые вакансии и компании, с которых они собраны.
- [ ] **K5. Ниша и регион вакансии.** Отбор по нише — по заголовку и описанию вакансии; регион
      вакансии — по её месту (город → страна по открытому справочнику, а не ручному списку).
      *Измеритель:* живые вакансии ниши в регионе.
- [ ] **K6. Надёжность ядра без людей.** Временный отказ источника не теряет работу (повтор с
      отсрочкой вместо DLQ), темп и бюджеты запросов, потолки ответа, SSRF — часть уже построена.
      *Измеритель:* доля заданий, ушедших в DLQ; ноль потерь при паузе источника.
- [ ] **K7. Отчёт ядра** — один отчёт (SQL/эндпоинт администратора) с измерителями K1–K6 по
      стране и по дням. По нему принимаются решения о следующих шагах.
- [ ] **K8. Минимальный выход** — список живых вакансий ниши (REST, уже есть) и ежедневное письмо
      (уже есть). Без новых фильтров и интерфейса.

## 2. Расширение ядра

- [ ] **E1. Австрия** — реестр Firmenbuch (HVD, API по ключу, CC BY 4.0), номер Firmenbuch в
      выходных данных сайта для подтверждения, немецкий язык в отборе ниши.
- [ ] **E2. Другие страны** — по одной: реестр, реквизиты на сайте, язык, валюта.
- [ ] **E3. Площадки-агрегаторы** — второй источник, только при разрешении или договоре (условия
      karriere.at и profesia.sk запрещают автоматическое чтение, project-notes §90): как источник
      названий компаний для K1. Вакансии — только с карьерной страницы компании (принцип 2).
- [ ] **E4. Ручной ввод компании** — третий источник, опция по желанию клиента: клиент называет
      компанию (название или сайт), дальше — тот же автоматический путь K2–K5; нет карьерной
      страницы со структурой — компания пропускается, клиент видит причину.

## 3. Критерий «ядро чётко работает»

Для Словакии, по отчёту K7, две недели подряд: очередь K1 движется каждый день; у пройденных
компаний сайт и карьерная страница определяются без ручного вмешательства; найденные страницы
собираются ежедневно; вакансии, исчезнувшие со страницы, закрываются; потерь заданий нет.
Числовые пороги (доля сайтов, число вакансий ниши) владелец задаёт по первым замерам K2–K4.

## 4. После ядра (глянец) — только когда выполнен §3

Интерфейс (SPA) и онбординг; сложные фильтры ленты; подписки на компании и уведомления;
отклики, собеседования, заметки; жалобы на данные; технологический профиль компании; сравнение
вакансий; снимки исходных данных (S3); безопасность публичного доступа
(ротация сессии, ограничение частоты входа); прочие улучшения корректности.

## 6. Расхождения с документами

Устранены в project-notes §98: бизнес-ТЗ и технический документ приведены к этому плану (ручной
ввод — третий источник по желанию клиента; площадки — источник названий компаний, а не вакансий; признак «скрытая» и покрытие исключены; ручного

расхождение **кода** с документами — пункты «Вне продукта» и «Вне ядра» в §5.
