## 0.2. Актуальность корневого README.md (обязательно)
Корневой `README.md` — краткая внешняя витрина проекта. Он поддерживается в актуальном состоянии при работе над **любым** кодом: если изменение затрагивает то, что заявлено в README, README обновляется в рамках той же задачи (часть Definition of Done), а не откладывается на потом.

README обновляется, **когда — и только когда — изменение затрагивает** хотя бы одно из:
- что за проект и что он делает (назначение, ключевой набор функций, область);
- технологический стек или версии (язык, фреймворк, БД, брокер и т.п.);
- архитектуру или набор развёртываемых модулей/сервисов;
- шаги сборки, конфигурации или локального запуска (команды, скрипты, порты, обязательные переменные окружения);
- статус проекта или сводку стадий/roadmap, приведённую в README;
- endpoints, точки входа или примеры, процитированные в README.

README **не требует** обновления, когда изменение внутреннее и ни один из пунктов выше не затронут — например, рефакторинг без изменения стека/архитектуры, внутренний багфикс, изменения только в тестах, или новые детали, которые живут в `docs/` и не меняют сводку README.

Правила:
- README держится на уровне сводки; глубокие детали остаются в `docs/technical-design.md`, а текущий статус — в `docs/project-notes.md`. В README правится только сводка, со ссылками на подробности.
- Если изменение затрагивает стек, шаги сборки/запуска или статус — правка README **блокирующая**: задача не считается завершённой, пока README не отражает реальность.
- Критерий при сомнении: «введёт ли теперь README в заблуждение того, кто читает его впервые?» Если да — обновить.

## 0.3. Коммиты и история версий выполняет владелец (обязательно)
Изменения в репозитории готовит ассистент, но **фиксацию в системе контроля версий делает только владелец**. Ассистент **не выполняет** `git commit`, `git push`, создание/переключение веток, теги, слияния и любые операции, меняющие историю или состояние гита; он не запускает эти команды и не предлагает их запустить от своего имени.

Правила:
- По завершении задачи ассистент оставляет рабочую копию с изменёнными/новыми файлами (working tree), **не коммитя их**, и отдельно даёт владельцу однострочное сообщение для коммита (в повелительном наклонении, суть изменения).
- Ветку, момент коммита и текст итогового сообщения определяет владелец; ассистентское сообщение — предложение, а не действие.
- Если для проверки ассистенту нужно состояние гита, допустимы только читающие команды (`git status`, `git log`, `git diff`); пишущие — нет.
- Инструкции по сборке, тестам и запуску ассистент даёт текстом; их выполняет владелец, если явно не попросил обратное.

## 0.4. Ведение `docs/project-notes.md` (стенограмма проекта) (обязательно)
`docs/project-notes.md` — сквозная **стенограмма проекта**, которую ведёт ассистент: после **каждого** изменения он **дописывает** в неё запись о том, что и зачем сделано. Это часть Definition of Done задачи, наравне с актуальностью README (§0.2), а не отдельная просьба владельца.

Правила:
- **Только дозапись, не переписывание.** Стенограмма растёт хронологически; уже сделанные записи (нумерованные срезы `§NN`) не редактируются и не переставляются — история не переписывается. Новая запись добавляется в конец, перед завершающим разделом-справочником.
- **Формат — как у существующих записей:** нумерованный срез `## §NN — <заголовок>` с подпунктами (что сделано и почему, ключевые файлы/конструкции, что проверяют тесты, отметка про README по §0.2, «что НЕ вошло»). Изменение только в документации запись это честно отмечает.
- **Шапка обновляется:** поле `Статус` в начале файла — краткая суть **последнего** изменения; прежнее значение сжимается в строку `Прежний статус` (бегущая компрессия истории).
- **Охват записи** — любое изменение репозитория рукой ассистента: код, схема, документация, конфигурация. Чисто внутренняя правка без содержательного эффекта записи не требует.
- Цель — чтобы владелец в любой момент восстановил ход проекта и понимал каждый файл и конструкцию (см. §0.1).
