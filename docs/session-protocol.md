# Регламент сессии ассистента (обязательный)

Дополняет [рабочий контракт](working-contract.md) и так же обязателен (контракт §0.6). Контракт
задаёт **правила кода и ролей**, этот документ — **порядок работы**: как начать сессию, как
вести срез, как сдать результат, когда проводить аудит. Выполняется по умолчанию, без
напоминаний владельца и без отчёта о выполнении в ответе.

Почему он есть: 2026-09-24 сессия началась неправильно — полный контракт не был прочитан
(файл в репозитории оказался урезан), результат выдан патчем вместо правки файлов, задача
расширена без разрешения (фильтр API), в ответе были рассуждения вместо команд, изменённая
сигнатура сломала компиляцию теста, запрос с датой упал на типе параметра, скрипт стенда содержал
безусловные команды. Каждый пункт ниже закрывает одну из этих ошибок.

---

## 1. Старт сессии (до любой правки)

1. **Контракт целиком.** Прочитать `docs/working-contract.md` полностью. Проверить, что в нём
   есть разделы §0, §0.1–§0.6, §1–§7 и далее. Если файл урезан или разделов нет — **стоп**: восстановить
   из истории git (`git log -- docs/working-contract.md`, `git show <rev>:docs/working-contract.md`),
   сообщить владельцу, работу не начинать до восстановления.
2. **Этот регламент** — целиком.
3. **Текущее состояние** — `docs/current-state.md` целиком; из `docs/project-notes.md` — шапку
   (`Статус`, `Прежний статус`) и две последние записи `§NN`. Весь журнал не читать — только
   нужные разделы по поиску.
4. **Какая версия кода — исходная.** Рабочая копия владельца (подключённая папка) может
   опережать GitHub: срез сделан, но ещё не закоммичен. Сравнить `git log -1` на GitHub с записью
   в шапке `project-notes.md` на устройстве; для каждого файла, который будет меняться, брать
   **версию с устройства**, если она отличается от GitHub (по размеру/времени изменения).
5. **Аудит не просрочен?** Посмотреть в `current-state.md` счётчик «срезов с последнего аудита».
   Если он ≥ 10 — следующий срез **аудит** (§5), новая функциональность — после него.
6. **Область задачи** (контракт §2.1) — понятна и согласована. Не понятна — вопрос
   владельцу, без начала работы.

## 2. Ведение среза

- Один срез — одна задача, одна проверка, один коммит владельца. Большую задачу делить.
- Выход за область (другой модуль «заодно», маршрут/DTO/формат JSON/статус-код, новая
  зависимость или файл) — **стоп и вопрос** (контракт §7). Найденное вне области — в ответе
  отдельной строкой «нужно решение владельца», без исправления.
- **Изменил сигнатуру** (конструктор, метод, record) — найти поиском **все** вызовы, включая
  тесты, и исправить их в том же срезе.
- **Запросы JPQL/SQL:** параметр, который может быть `null`, не ставить в условие
  `:param is null` без контекста типа (дата/время — только через вычисленный в Java признак или
  рядом с колонкой того же типа, см. project-notes §68).
- **Проверки, доступные в среде ассистента,** выполнить до выдачи: компиляция и прогон новых
  тестов изолированно (`javac` с минимальными заглушками, если Maven недоступен); для скриптов
  стенда — `bash -n`, сверка имён таблиц/колонок с миграциями, полей JSON — с DTO, проверка
  разборщиков вывода на образце. Что проверить не удалось — назвать в ответе одной строкой.
- Правила контракта §3 (≤5 параметров, нет однобуквенных имён и «магических» чисел, нет
  циклов пакетов, JavaDoc, тесты) — проверить по изменённому коду **до** выдачи.

## 3. Сдача результата

- Файлы — **прямо в рабочую копию владельца** (не патч, не архив, не текст для копирования).
  Перед записью файла, изменённого владельцем после последнего чтения, — перечитать.
- Ответ — строго по контракту §0.5: файлы списком → команды (сборка → тесты → прогон) →
  комментарий для коммита на английском → следующие шаги.
- **Команды с условием помечаются условием** («только если `docker compose ps` не показывает
  postgres»). Команда, не нужная для проверки среза, не выдаётся.
- Для прогона — что должно получиться и где смотреть результат (файл отчёта). Отчёты
  прогонов ассистент читает сам по слову владельца «готово».
- Вывод сборки владелец сохраняет в `target/verify.log`
  (`mvn -B -ntp verify 2>&1 | tee target/verify.log`) — ассистент читает ошибки оттуда и из
  `*/target/surefire-reports`.

## 4. Завершение среза и сессии

- `docs/project-notes.md` — запись `§NN` и шапка (контракт §0.4).
- `docs/current-state.md` — обновить, если срез изменил что-либо из описанного там (модули,
  ключевые классы, соглашения, стенды, статус плана); **счётчик срезов +1** всегда.
- README — по контракту §0.2.
- Облачная (рабочая) копия репозитория ассистента удаляется по окончании работы: в ней не
  должно оставаться незакоммиченных изменений (иначе автоматические проверки среды требуют
  коммита, которого ассистент по контракту не делает).

## 5. Срез-аудит (каждые 10 срезов)

Когда счётчик в `current-state.md` достигает 10, следующий срез — аудит, **без новой
функциональности**. Область — весь код, изменённый с прошлого аудита (по записям
project-notes), плюс документы. Проверяется:

1. **Контракт §3** по изменённому коду: параметры ≤5, имена, константы, JavaDoc, SRP, SQL в
   сервисах, циклы пакетов, транзакции, таймауты внешних вызовов.
2. **Дубли и мёртвый код:** две реализации одного правила, неиспользуемые методы/классы/
   настройки, конструкторы «только для тестов» без нужды.
3. **Согласованность:** одинаковые задачи решены одинаково (нормализация, гейт, пагинация,
   обработка ошибок источников); настройки — в `application.yml` с комментарием.
4. **Тесты:** у изменённого поведения есть тест; нет тестов, проверяющих уже несуществующее.
5. **Документы:** README, `current-state.md`, `technical-design.md` (ADR), план
   (`roleorienta-plan-korrektirovka.md`), комментарии в `application.yml` — соответствуют коду;
   контракт не урезан.
6. **Автоматические проверки (§6)** — работают и не отключены.

Результат: запись `§NN — Аудит` в project-notes (что найдено, что исправлено, что вынесено на
решение владельца); исправления — минимальные, в рамках найденного; счётчик в
`current-state.md` сбрасывается в 0.

## 6. Автоматические проверки в CI (цель)

Для определения требований к коду - см. working-contract.md. Все требования описаны там.

Правила кода проверяются сборкой, а не памятью. Целевой набор (пункт C4 плана, вводится
отдельным срезом):

- **Checkstyle** (`mvn verify` падает при нарушении): не больше 5 параметров у методов и
  конструкторов; нет однобуквенных имён (кроме индексов цикла, если разрешено контрактом —
  сейчас не разрешено); длина метода; JavaDoc у публичных классов и методов.
- **ArchUnit** (тесты): нет циклов пакетов; исходящие HTTP-запросы воркера — только через
  `SourceHttpClient`; разбор XML — только через `SafeXml`; контроллеры не обращаются к
  репозиториям напрямую.

До введения — те же пункты проверяются вручную по §2 и §5. После введения нарушение
исправляется, а не подавляется; исключение — только с разрешения владельца и с записью причины.

## 7. `docs/current-state.md` — короткий документ о состоянии

Две–три страницы, читаются в начале каждой сессии (§1.3). Содержит: назначение и границы,
модули и ключевые пакеты/классы, путь данных (обнаружение → сбор → нормализация → лента),
соглашения кода, настройки, стенды (`target/*.sh`), статус плана, **счётчик срезов с
последнего аудита**. Это «как устроено сейчас», без истории — история остаётся в
project-notes. Устаревшее в нём — дефект, исправляется в том же срезе.
